# SGS Recharge Advisor

> 三国杀 OL 活动充值与消费规划 Skill  
> 解析官方活动公告，搜索低成本充值消费方案，并对方案进行逐笔复核与可审计的最优性验证。

[![License](https://img.shields.io/badge/license-Apache--2.0-green.svg)](./LICENSE)

## 简介

`sgs-recharge-advisor` 是一个面向《三国杀 OL》活动的充值与消费规划 Skill。

它读取玩家提供的：

```text
aim.txt
```

以及当期官方活动公告：

```text
note.pdf
```

分析：

- 充值档位
- 首充额外到账
- 单笔充值返还
- 每日累计充值
- 活动累计充值
- 消费奖励
- 礼包
- 抵价券
- 签到
- 周卡 / 月卡
- 道具兑换
- 概率奖励
- 活动时间
- 商品限购
- 奖励领取窗口

然后搜索满足玩家目标的充值与消费方案。

这个项目的目标并不只是：

> “算一个看起来比较划算的充值方案。”

而是：

> **在当前规则和玩家状态允许验证的范围内，寻找可执行的低成本方案，并说明它为什么可行、为什么优于其他候选，以及哪些结论仍然没有得到证明。**

因此，本项目严格区分：

- 找到一个可行方案；
- 找到一个比历史方案更好的方案；
- 已验证该方案能够完整执行；
- 已证明该方案在给定有限搜索空间中最优。

如果证据不足，不会把“看起来不错”写成“已经证明最优”。

## 3. `aim.txt` 是什么？

`aim.txt` 用来告诉模型：

- 你想得到什么；
- 预算是多少；
- 当前账户有什么资源；
- 哪些首充已经用过；
- 有没有周卡 / 月卡；
- 有没有抵价券；
- 当前有多少元宝；
- 还有哪些会影响方案的账户事实。

例如：

```text
目标：

- 至少获得 30 个祈福灯
- 至少获得 2 个传世玉玺
- 在满足目标的前提下尽量降低现金支出

预算：

500 元以内

期初账户：

元宝：12000

首充状态：

6 元：未使用
12 元：已使用
30 元：未使用
68 元：未知
128 元：未使用
328 元：未使用
648 元：未使用

抵价券：

2000 元宝券 × 1
有效期至 9 月 8 日

周卡：

剩余 3 天

登录情况：

活动期间每天均可登录
```

不知道的信息可以直接写：

```text
未知
```

**不要为了让输入看起来完整而猜。**

如果某个未知状态会改变最低现金结论，Skill 会将其列为需确认项，或者给出条件分支。

---

## 4. `note.pdf` 是什么？

`note.pdf` 应当是本期活动的完整官方公告。

推荐上传完整 PDF，而不是只上传几张截图。

因为活动规则经常会分散在不同位置：

```text
第一页：奖励表

下一页：礼包限购

表格下面：抵价券限制

另一章节：活动结束时间

脚注：奖励不能重复领取
```

如果只上传部分页面，可能会遗漏对方案有决定性影响的限制。

# 独立充值记账

本项目不会直接使用：

```text
“双倍”
“三倍”
“这档很赚”
```

这样的语言描述替代实际计算。

一笔充值会尽量拆成：

```text
充值本体
+
首充额外到账
+
公告单笔返还
+
每日累计奖励
+
活动累计奖励
=
实际资源变化
```

同时分别维护：

```text
现金

充值面额

账户元宝

首充资格

每日充值进度

活动累计充值

单笔奖励次数

消费进度

抵价券

随机收益
```

例如：

```text
“30 元双倍”
```

并不一定代表首充。

它可能实际上是：

```text
3000 基础到账
+
3000 公告单笔返还
=
6000
```

也可能是：

```text
3000 基础到账
+
3000 首充额外到账
+
3000 公告单笔返还
=
9000
```

因此必须拆开来源判断。


```text

每日累计奖励

抵价券
```

# 为什么不能只用贪心算法？

活动通常包含大量离散门槛，例如：

```text
充值 30 元触发奖励

充值达到 100 元再送奖励

某个单笔奖励每天只能领取一次

某礼包每天限购一次

某张券 3 天后过期

消费达到 100000 元宝额外送奖励

某个首充档位只能使用一次
```

因此：

> 单笔收益率最高

不代表：

> 整个活动方案现金最低。

类似地：

> 使用抵价券后这一单支付更少

也不一定代表：

> 最终方案更优。

例如使用券可能降低实际消费进度，从而错过更大的累计消费奖励。

因此，本项目不能简单地：

```text
对充值收益率排序
→ 每次选最好的
```

然后就宣布最优。

# 搜索与最优性证明

Skill 使用：

```text
支配关系
    ↓
交换论证
    ↓
建立有限搜索边界
    ↓
完整枚举剩余候选
```

## 支配剪枝

只有在能够证明：

> 候选 A 可以替代候选 B 的每个相关未来可行续程，而且最终目标不更差

时，才允许删除 B。

不能仅仅因为：

```text
A 到账更多
A 现金更少
A 进度更高
A 的券快过期
```

就直接删除其他候选。

因为这些状态可能影响未来：

```text
消费门槛
首充资格
奖励领取状态
券机会成本
商品限购
换日
```

---

## 有限枚举

剩余搜索空间可能包括：

```text
充值次数
×
充值日期
×
首充使用
×
周卡 / 直购
×
单笔奖励
×
累计门槛
×
礼包购买
×
抵价券匹配
×
消费安排
×
续费时间
```

现金以“分”作为整数单位。

元宝、物品和进度使用整数。

概率使用精确分数或明确误差。

## 什么情况下才能写“最优”？

最优性证书需要至少说明：

```text
优化目标排序

搜索空间的有限边界

采用的支配 / 剪枝规则

实际枚举范围

胜出方案的目标值

为什么所有更低现金候选都不可行

同现金候选之间如何比较
```

如果代码没有运行、搜索没有穷尽，或者关键条件未知，只能报告：

> 已找到可行方案，最优性未验证。

不能直接写：

> 全局最优。

# 可执行性验证

找到一个数学上看起来正确的方案，还不够。

Skill 会对最终方案执行**逐笔状态重放**。

---

## 重放状态

包括：

```text
日期 / 时间

现金

账户元宝

抵价券批次

抵价券到期时间

目标物品

首充资格

每日充值

活动累计充值

累计消费

已领取奖励门槛

商品限购

周卡 / 月卡领取状态
```

每一步都必须保证：

```text
资金不透支

奖励已经获得才能使用

抵价券没有过期

商品没有超过限购

首充没有重复使用

预算没有超出

硬目标最终达成
```

---

## 总计反推

逐笔重放后，还会独立进行一次总计核对。

例如：

```text
期初元宝
+
确定收入
-
消费支出
=
期末元宝
```

券则单独计算：

```text
期初券
+
获得
-
使用
-
过期
=
期末券
```

目标物品同样分别计算。

最终：

> 逐笔重放结果必须与总计反推结果一致。

如果最终总数正确，但中间某一天发生资金透支，这个方案仍然不可执行。

# 随机收益

对于概率类活动，本项目严格区分：

## 保证收益

无论随机结果如何，都可以取得的资源。

## 已验证数学期望

拥有完整概率分布，并可以根据实际随机结果执行策略时计算出的数学期望。

## 经验 / 均值资金情景

根据：

```text
玩家经验
经验均值
经验保底
```

构建的场景。

三者不会混用。

特别是：

```text
E[f(X)] ≠ f(E[X])
```

例如：

```text
50% 概率得到 0 元宝
50% 概率得到 10000 元宝
```

平均值虽然是：

```text
5000
```

但这不意味着玩家一定可以购买一个：

```text
6000 元宝
```

的商品。

所以：

> 期望资源不能被当作保证资金提前消费。

# 历史方案与 GT

对于已经存在历史方案的活动，本项目可以将其作为：

```text
GT
```

即 Ground Truth / 回归性能基线。

但：

> **GT 是基线，不是真理。**

Skill 不会因为历史方案存在，就默认它是最优答案。

---

## GT 验证流程

Skill 会：

1. 保存历史动作；
2. 保存原始统计口径；
3. 独立重新计算历史现金和收益；
4. 构造新的合法候选；
5. 使用相同口径进行比较；
6. 如果找到更好的合法候选，则历史比较 FAIL；
7. 如果关键证据不足，则标记 `NOT_VERIFIED`。

如果历史方案只存在局部算术错误，会修正局部问题。

不会为了让回归测试通过而直接废弃整个历史方案。

---

# 四层验证状态

历史回归和正式分析使用四层验证：

| 层级 | PASS 所需内容 |
| --- | --- |
| 收益加总 | 已记录动作的现金和收益能够独立复算 |
| 历史口径比较 | 新候选按照相同口径不差于 GT |
| 消费可行性 | 日期、资金、券、物品、限购、预算和硬目标全部通过 |
| 最优性 | 可行性通过，并完成有限搜索及更低现金不可行证明 |

状态使用：

```text
PASS

FAIL

NOT_VERIFIED

NOT_APPLICABLE
```

例如：

```text
收益加总：PASS
```

并不意味着：

```text
整体最优性：PASS
```

不同层级必须分别验证。


# 当前边界

以下情况可能导致结果只能是：

```text
条件方案

NOT_VERIFIED

已找到可行方案，最优性未验证
```

包括：

- 玩家没有提供会改变结论的账户状态；
- 活动公告存在无法消除的歧义；
- 商品实际可获得性无法确认；
- 概率分布不完整；
- 搜索没有完整执行；
- 某些历史入口只有玩家观测结果，但无法确认其真实机制；
- 某个随机重复动作无法建立有限边界；
- 官方公告与账户输入存在冲突。

在这些情况下，Skill 会继续完成能够证明的部分，并明确标注剩余不确定性。

# 设计原则

## 公告优先于经验

一般玩家经验不能覆盖当期明确官方公告。

---

## 公告规则与账户事实分开

玩家明确提供的：

```text
账户余额
首充状态
已有道具
已有抵价券
商品可获得性
```

属于当前样本事实。

历史活动中的事实不能自动迁移到新活动。

---

## 每一笔资源都要有来源

分别记录：

```text
现金

充值面额

基础到账

首充额外到账

单笔奖励

每日累计奖励

活动累计奖励

抵价券

随机资源
```

避免重复入账。

---

## 没有证明，就不要写“最优”

搜索不完整时，可以交付一个优秀的可行方案。

但不能把：

```text
目前找到的最好方案
```

自动写成：

```text
全局数学最优
```

---

## GT 是基线，不是真理

历史方案用于：

```text
回归测试
性能比较
行为验证
```

同时允许被新的合法方案推翻。

---

## 结果必须能够重放

一个：

```text
最终总计正确
```

但：

```text
中途资金透支
```

的方案仍然属于不可执行方案。
